# VPS 内部模拟: 在真实内核上独立复现 C2 结论 (2026-10-20)

> 目标: CI 的 C2' 5h 成对门禁是在 QEMU guest 里跑出来的。本实验在**真实内核 (7.2.11-tcpboost+)**、
> **真实 TCP 栈 / 真实 qdisc / 真实 pacing** 上独立复现, 排除"QEMU 数字是虚拟化假象"的可能。

## 1. 平台与隔离

| 项 | 值 |
|---|---|
| 主机 | 104.243.21.24:26018 (fleet 实验机, 2 核 / 1GB / 无真实流量时段) |
| 内核 | 7.2.10-tcpboost+ → **7.2.11-tcpboost+** (含 C2 代码, 旧内核保留可回退) |
| 隔离 | **netns + veth pair**: 损伤只加在 veth 上, **完全不碰宿主 `lo` / `eth0`** |
| 流量 | 全部在 netns 内部虚拟网卡, **不产生任何公网流量** (provider 不可见) |
| 业务 | `xr.service` (xray) + `argo.service` (cloudflared) 照常运行, 实验期间无中断 |

**为什么必须隔离**: 该机承载 xray CDN 后端, 出站回源走宿主 `lo`。CI 那套 `tc qdisc add dev lo root netem`
如果照搬到这里, 会把 150ms RTT + 0.5% 丢包注入到真实用户流量里 —— 所以改用 netns。

## 4. 方法学修正 (踩坑记录)

1. **`ss -tin` 的 `delivery_rate` 双计**: iperf3 每条流有控制连接 + 数据连接两个 socket,
   都被 `dport = :<port>` 命中 → `active_streams` 显示 16 (实为 8), `total_mbps` 是真值的 ~2×。
   **裁决一律用 per-stream 真值** (server log 的 Interval 表), 不用 `ss` 汇总。
2. **限速会掩盖"总量"但不会掩盖"不公平"**: 限速 100mbit 时总吞吐看着正常 (均分),
   但 per-stream 差异巨大 —— **总量正常 ≠ 公平**, 单看 total 会误判"病理不存在"。
3. `analyze_matrix` 的防伪门 (`validate_series`, 恒值占比 >20% 报错) 会对"完美均分"的数据报假警,
   需改用 `scripts/analysis/per_stream_stats.py` 看原始分布。

| 流 | mean | min | 地板占比 (<12Mbps) |
|---|---:|---:|---:|
| 5204 | 4.70 | 0.00 | 93.7% |
| 5201 | 6.66 | 0.00 | 82.8% |

## 6. 24h 成对 A/B 结果 (终审: FAIL)

设计修正: 实验两次被杀 (段收尾死锁 → 已修; **宝塔面板每日 03:30 reboot 计划任务连坐** → 已注释),
最终以 6 段 × 2h (每臂 3 段 / 6h) 完成, 2026-10-21 16:10 UTC 收工。

### 段级数据 (每段 2h, 8 流)

| seg | c2 | total_mean | total_med | min_mean | 活跃时均值 | 零速秒% |
|---|---|---:|---:|---:|---:|---:|
| 0 | 0 | 77.0 | 78.8 | 0.81 | 10.71 | 10.2% |
| 2 | 0 | 76.2 | 77.7 | 0.73 | 10.65 | 10.6% |
| 4 | 0 | 77.0 | 79.2 | 0.84 | 10.78 | 10.7% |
| 1 | 1 | 72.0 | 70.5 | 0.53 | 10.49 | 14.2% |
| 3 | 1 | 69.9 | 68.1 | 0.44 | 10.36 | 15.6% |
| 5 | 1 | 71.1 | 68.9 | 0.51 | 10.45 | 14.9% |

臂级: c2=0 → total 76.7 / min 0.79 / 活跃 10.71; c2=1 → total 71.0 / min 0.49 / 活跃 10.43。
段级方差极小 (每臂 3 段几乎重合) → **系统性差异, 非噪声**。

### 三判据 (CI 预注册口径)

| 判据 | 结果 | 裁决 |
|---|---|---|
| 1. total_mean(c2) ≥ 1.05×base2 | 71.0 vs 80.5 (**−7.4%**) | **FAIL** |
| 2. min_stream_mean(c2) ≥ base2 | 0.49 vs 0.79 (**−37.9%**) | **FAIL** |
| 3. starved_s(c2) ≤ 1.5×base2 | 两臂均为 0 (阈值口径下未检出) | PASS/N-A |

**VERDICT: FAIL (真实内核 + 限速环境)。与 CI (total +39.2% / min +36.1%) 方向完全相反。**

### 机制分析 (为什么 CI 与 VPS 相反)

- **活跃时吞吐两臂几乎相同** (10.43 vs 10.71, −2.6%) → 差异不在"跑得慢", 在 **c2 臂断流秒多 ~40%** (零速秒 14-16% vs 10-11%)。
- **环境错配假说 (主嫌疑)**: netem `rate 100mbit` 是 token bucket, 允许突发 (单流瞬时冲到 117-167 Mbps)。
  突发抬高 `max_bw` 估计, 而巡航时 `bw_latest`(~10-12 Mbps/流) → C2 触发条件 `bw_latest×2 < max_bw` **恒为真** → 频繁重探测 → probe 期 pacing 切换 → 更多排队/丢包/断流。
  CI 的 QEMU 无硬限速, max_bw 估计贴真实能力, 触发条件只在真实深跌后成立。
- 不能排除的备选: 真实宿主内核网栈与 QEMU guest 的差异本身。

### 对车队决策的影响 (重要)

- CI 的 PASS **只在其无硬限速环境成立**; 本实验证明 C2 在"存在硬瓶颈"场景**净负收益** (total −7.4%, 最弱流 −38%)。
- 车队真实链路虽无人工限速, 但**真实带宽瓶颈与硬限速同属"硬上限"类约束**, 风险同类。
- **结论: 撤回车队部署建议。C2 维持主线默认 off (不动); 若未来要试点, 必须先在目标链路做小流量 A/B, 且预注册判据须加入"断流秒"守卫。**
- CI PASS + VPS FAIL 并存的教训: **机制验证结论只在验证环境内成立**, 外推前必须做目标环境复现——本实验正是这一步, 它防止了一次可能有害的部署。

## 7. 巡检机制 (早发现问题, 不等 24h)

两层保险:

1. **VPS 端每小时自检** (cron `7 * * * *` → `/root/vps_sim_health.sh`) → 追加 `/var/log/tcpboost-sim/health.log`。
   每次记录: 段进度 / 当前 c2 值 / cgroup CPU+内存 / iperf3 进程数 / netem+netns 存活 / 业务状态 /
   采样器活性 (CSV 末行滞后秒数) / **每流最近速率**。
2. **本机每 6 小时拉一次摘要** (长跑 job, 4 次) → 主动汇报, 不用等 24h 才发现问题。

**自动告警判据** (自检脚本直接打 WARN): unit 非 active · iperf3 进程 <8 · netem qdisc 丢失 ·
netns 丢失 · `xr.service` 非 active · cloudflared 进程消失 · 采样器停摆 >300s · 存在 0 速流。

## 8. 已知限制

- 有限速 (CI 无) → 与 CI 数字**不可直接比大小**, 只能比**方向与相对幅度**
- 2 核小机: 争抢强度受 CPU 供给影响, 与 CI 的 QEMU 供给不同
- 单机 client+server 共享 CPU → server 侧有额外排队噪声
- 24h 只能覆盖有限的"深跌"事件数, 统计力弱于 CI 的 17945s × 8 流
